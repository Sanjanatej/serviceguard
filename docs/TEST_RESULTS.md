# ServiceGuard Test Results

All tests were run on Ubuntu 24.04 (WSL 2) against a local Nginx test site on
port 8080. Checks ran every 3 seconds, with a failure threshold of 2
consecutive failed checks before an incident is opened.

Raw evidence: `evidence/*.log` and `logs/incidents.jsonl`.
Summary table: `evidence/incident-summary.md` (generated by
`scripts/summarize_incidents.py`).

## Results

| Test | Failure injected | Detected as | Recovery behavior | Outcome |
|---|---|---|---|---|
| Baseline | None | `Status: OK` (health 200, home 200) | Not needed | Healthy |
| A | `systemctl stop nginx` | connection refused or unreachable | Config test passed, restart succeeded, `is-active` returned `active` (1 attempt) | Resolved automatically, ~6.5s detected downtime |
| B | Invalid directive added to site config, then nginx stopped | connection refused or unreachable | Config test failed on both attempts, restart never ran | Escalated, resolved by manual fix, ~45.5s (includes human time) |
| C | `/health` file removed (nginx still running) | `health: unexpected status 404 (expected 200)`, `home` stayed OK | Commands succeeded twice, but the problem persisted | Escalated, resolved by manual fix, ~25.6s (includes human time) |

Unit tests: 4 passed (`tests/test_checker.py`: success, wrong status, missing
text, connection refused).

## What each test shows

- **Test A:** detection, incident logging, and a successful automatic recovery
  that was verified by re-checking the service over HTTP.
- **Test B:** recovery is safe. ServiceGuard refuses to restart onto a broken
  config, records nginx's own error (file and line number), and escalates.
- **Test C:** a clean restart does not mean a healthy service. The recovery
  commands succeeded, but only the HTTP check revealed the problem was not
  fixed. Not every failure can be fixed by a restart, so ServiceGuard escalates
  after the attempt limit.

## How to read the downtime numbers

- Downtime is measured from the first failed check, not the exact moment the
  failure happened, so it is "detected downtime".
- Only Test A's figure is automated recovery time. Tests B and C include the
  time a human took to fix the problem.

## Limitations

- One run per scenario, so these are demonstrations and not statistics.
- Single local machine and single service. There is no cloud deployment,
  alerting, or metrics system.
- The consecutive-failure counter keeps counting after the threshold, so logs
  show lines like `DOWN (5/2)`. This is cosmetic.
- The sudoers rule allows only `systemctl restart nginx` and `nginx -t`.
  ServiceGuard cannot stop services or run other privileged commands.
